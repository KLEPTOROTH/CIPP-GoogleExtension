## 1. Locked system boundaries

- Web app owns view composition, keyboard interaction, and typed error rendering.
- Core/action layer owns cross-provider suspend/resume semantics (`success-both`, `partial`, `failure-both`).
- Provider adapters own side-effect execution and provider-specific failure signaling.
- Audit surface is read-only in v0.1, filtered/paginated by query state.

Out of scope (must not creep in this phase):

- License mutation/editing.
- Non-phase-1 policy automation.
- New auth model work.

## 2. Canonical state transitions (user row)

States: `Active`, `Suspended`, `Inconsistent`, `Unknown`

- `Active -> Suspended`: both adapters succeed on suspend.
- `Active -> Inconsistent`: one adapter succeeds, one fails.
- `Suspended -> Active`: both adapters succeed on resume.
- `Suspended -> Inconsistent`: one adapter succeeds, one fails.
- `Inconsistent -> Active|Suspended`: side retry converges both channels.
- `Unknown`: identity data missing/non-deterministic; no optimistic mutation assumptions.

Lock rule:

- `Inconsistent` must always expose explicit retry affordance (`Retry Google` / `Retry M365`).

## 3. Trust boundaries and failure model

- UI must treat action/result payloads as untrusted input and render typed error envelopes.
- Route parsing failures and config/runtime failures must resolve to machine-parseable `code` + `message` contract.
- Dry-run behavior may return transport `200` with internal dry-run status marker for deterministic UI handling.
